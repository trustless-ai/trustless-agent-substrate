# TAS Demo Deterministic E2E and Subagent Usability Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` for the implementation tasks and `superpowers:verification-before-completion` for each acceptance run. Deterministic E2E must pass before human-supervised Subagent usability testing begins.

**Goal:** Prove that three isolated Agent/TAS pairs can self-register, self-join, discover the Demo TAWG, collaborate through offline Chat for at least three rounds, recover across process replacement, and settle reproducible cumulative points.

**Architecture:** A test harness starts public local infrastructure and injects provider-neutral test Clients at the TAS composition boundary. Automated Actor drivers use only MCP calls and the same public state transitions. The second gate replaces those drivers with independent Subagents guided by Bootstrap, TAS, and Role Skills. Runtime state is isolated below one ignored `.tas-e2e/<run-id>/` root.

**Tech Stack:** TypeScript/Vitest, MCP stdio client APIs, viem, Anvil, the Demo Foundry project, local Git repository mirror, offline Chat broker, and Codex Subagents for the usability gate.

**Spec:** `docs/superpowers/specs/2026-08-22-tas-demo-vertical-slice-design.md` Sections 7 and 11-14 plus all preceding Slice A-D plans.

## Global Constraints

- Begin only after Slices A-D pass their complete gates.
- The harness prepares public infrastructure and test funds only.
- Every Actor creates or loads its own wallet, passes its own inline credential, registers its own ERC-8004 identity, registers its own Profile membership, and submits its own role transactions.
- Do not seed a pre-registered Agent ID or a pre-joined Profile member.
- Actor labels such as `contributor-a` are test labels, never ERC-8004 IDs.
- Each Actor owns a distinct TAS process, config root, credential file, cursor state, and Repository checkout when one is needed.
- No test-only option may enter production TOML or MCP.
- Scenario Chat messages flow through the Fake transport and production Chat MCP schemas.
- Deterministic automated Actor drivers must not import TAS Core; they act as Hosts over MCP.
- The Subagent receives no direct business command beyond bootstrap input, public locators, and messages delivered through the scenario.
- A replacement Subagent receives the same actor directory but no prior conversation context.
- Never accept a Subagent-only success that cannot be repeated by automated E2E.
- No `.tas-e2e/` path may be staged or committed.

## Task 2: Build the MCP Host Harness

**Files:**

- Create: `test/e2e/host/tasProcess.ts`

- Create: `test/e2e/host/createE2eTasApp.ts`
- Create: `test/e2e/host/host.test.ts`

- [ ] **Step 1: Write failing stdio lifecycle tests**

Start one TAS process from an actor config, complete MCP initialization, list tools, call a read tool, call a sensitive tool with an inline credential, close the connection, and prove stdout contained only MCP frames while logs contained no credential. Run two processes simultaneously and prove both observe the same Repository/DA commit and Chat event stream through their separate Client instances.

- [ ] **Step 2: Implement a generic Host boundary**

The harness may initialize/list/call MCP and manage process lifecycle. It contains no onboarding, role, retry, or Demo business logic. Actor drivers and Subagents decide which tools to call.

`test/e2e/host/main.ts` is a source-only, test-only stdio composition entrypoint. It imports production `createTasApp` and supplies the already-designed dependency interfaces from an explicit E2E descriptor below the validated run root. `createE2eTasApp.ts` injects the local Repository Client, local Git DA Client, and file-backed Telegram/Discord Clients. The production CLI, TOML schema, MCP inventory, and package contents gain no E2E selector or path.

`tasProcess.ts` starts this test source entrypoint for E2E runs. Normal package and integration tests continue to start the production entrypoint.

- [ ] **Step 3: Prove process and directory isolation**

Reject two TAS processes claiming the same member instance. Allow different Agent IDs in separate actor roots. Prove no process changes its instance tuple during its lifetime.

## Task 4: Run the Deterministic Three-round Happy Path

**Files:**

- Create: `test/e2e/actors/contributor.ts`
- Create: `test/e2e/actors/evaluator.ts`
- Create: `test/e2e/demo.clean.test.ts`

- [ ] **Step 1: Write the failing three-round scenario**

Require this exact high-level path:

```text
round 1: contributor A + contributor B submit -> evaluator scores -> settle
round 2: contributor A process replaced -> reload -> submit -> evaluator scores -> settle
round 3: evaluator process replaced -> reload -> score A and B -> settle -> complete
```

Each contribution must use DA put/get, a deterministic contribution ID, a Chat mention, and on-chain query confirmation. Each evaluation must read the DA bytes before scoring. Each round settlement must verify per-round and cumulative points.

- [ ] **Step 2: Implement MCP-only Actor drivers**

Drivers parse public MCP results and call only discovered tools. They may retain their own cursor and public business identifiers in the actor root. They do not import Core services, Clients, contract storage helpers, or private harness deployment objects.

## Task 6: Define and Run the Subagent Usability Gate

**Files:**

- Create: `test/e2e/subagent/README.md`
- Create: `test/e2e/subagent/SCENARIO.md`
- Create: `test/e2e/subagent/acceptance.schema.json`

- Modify as findings require: `tawg/demo/skills/roles/contributor.md`
- Modify as findings require: `tawg/demo/skills/roles/evaluator.md`

- [ ] **Step 1: Document the information boundary**

The Evaluator first receives only the Bootstrap Skill plus chain/Identity Registry locator. After it publishes its public Agent ID and deployment completes, all Subagents receive only the Bootstrap Skill plus TAWG locator. Scenario work arrives through Fake Chat.

- [ ] **Step 2: Start three independent Subagents**

Assign each one an isolated actor root and responsibility. Explicitly tell them they are not alone and must not alter another actor's files. They must follow Skill guidance, use the generic MCP Host boundary, and report only public results.

- [ ] **Step 3: Replace processes and Agents across rounds**

After round one, terminate Contributor A's TAS and Subagent. Spawn a fresh Contributor Subagent with the same actor root and no conversation inheritance. Before round three completion, do the same for the Evaluator. The replacements must rediscover identity, membership, Workflow verification, Role Skill, Chat cursor, and on-chain state.

- [ ] **Step 4: Classify every failure before changing code**

Record one of:

```text
skill_gap
mcp_gap
agent_judgment
expected_contract_rejection
test_infrastructure
```

Fix Skill/MCP gaps, add or update the deterministic test that reproduces the issue, rerun deterministic E2E from clean state, then rerun the affected Subagent stage. Never give an undocumented workaround to make the run pass.

- [ ] **Step 5: Validate the acceptance record**

The final record contains only public IDs, tool names, transaction hashes, DA references/digests, round IDs, Chat event IDs/cursors as opaque values, points, restart boundaries, and failure classifications. Validate it against `acceptance.schema.json`.

- [ ] **Step 6: Commit durable guidance fixes**

Commit only the scenario definition, schema, deterministic regression tests, and reviewed Skill improvements. Do not commit the run record or any `.tas-e2e/` content.
